# CSUCampusCraft 测试与验收用例

本文件定义项目验收用例、测试环境、发布门槛和取证方式。需求与规则见[需求与业务规则](需求与业务规则.md)，页面入口见[页面清单与原型](页面清单与原型.md)与[系统设计与路由](系统设计与路由.md)，字段和数据库核对方法见[数据库设计](数据库设计.md)。

M0 工程初始化与 STEP02 基础设施已完成，STEP03 用户端公开浏览已通过自动实测，组员交叉复核待补；其余业务模块仍待开发。MySQL 基线的构建、导入、双端联通、重启与共享图片结果记录在 INIT-01 至 INIT-05。TST-01 至 TST-40 随业务开发执行，其中 TST-36 是 P1 选做，其余为 P0。控制台、普通顾客管理和相册维护仍待开发；用户端公开目录页面及其只读实测见 STEP03 记录。页面行为、业务事务、支付和发货只按对应 TST 的实际结果判定。

## 环境与夹具

- 用待验收提交分别构建用户端和管理端，指向同一套可重建的 MySQL 8.4/InnoDB 隔离数据库。记录完整 Git SHA、工作区是否有修改、JDK、Maven、MySQL、浏览器版本和启动命令。若验证尚未提交的工作区，另保存 `git status`、相关差异及受测文件 SHA-256，不能用 HEAD 代替实际受测文件。当前初始化访问端口为 8080 和 8081。两端分别使用 `CSUCAMPUSCRAFT_USER_SESSION` 和 `CSUCAMPUSCRAFT_ADMIN_SESSION`。
- 按 [README](../README.md) 分别在空库导入结构脚本与演示脚本。演示库包含 4 个账号、15 个分类、60 个商品、100 条相册记录、10 条购物车记录、10 张订单和 20 条订单明细。五个一级主题各有两个二级分类，每个二级分类有 6 个商品。
- 使用 `alice`、`bob` 两个普通账号验证本人数据和跨账号隔离。准备管理员、禁用账号和两个独立会话。每个变更场景使用可恢复夹具，区分种子历史订单和本次应用新建订单。
- 备齐可筛选可翻页的上架商品、有货和售罄商品、下架商品、无相册和缺图商品，以及库存仅 1 件的独立测试 SKU。购物车品种上限测试确保至少有 21 个可加购 SKU。并发和故障注入用例使用独立请求、真实 Service 事务入口和独立数据库连接。
- 管理端新范围准备普通顾客启停夹具、一个管理员目标 ID、含不同状态订单的 CUSTOMER，以及两个父商品和各自相册。启停和相册副作用分别核对 `store_user`、`product`、`product_image`，不能仅凭提示框判定成功。
- 在桌面 Chrome 或 Edge 的 1366×768 和 1920×1080 视口检查主流程、空状态、错误提示和提交中的交互。测试使用虚构收货地址，证据中隐藏密码、Cookie 值、确认令牌及个人信息。

### 历史 MySQL 底层回归记录（精确版本缺失）

- 在隔离库检查 `alice` 的种子车，6 条中有 3 条因库存不足、下架或售罄而失效。在 SQL 测试事务中清空并按演示数量加入两种商品后，得到 2 条有效记录和 85.00 元合计，变更已回滚。
- 从两端实际 Spring 上下文调用 `CategoryMapper.insert`，分类 `id` 由 MySQL `AUTO_INCREMENT` 发号。管理端和用户端分别回填 504、505，与同连接的 `LAST_INSERT_ID()` 一致，并按回填值查到新增记录。测试分类已回滚，两端 JDBC 会话时区均为 `+00:00`。
- 两个独立 `READ COMMITTED` 事务对同一库存为 1 的商品执行锁定读。观测到第二个事务等待，第一个事务扣库存并提交后，第二个事务读到库存 0。这是 InnoDB 机制验证。两账号真实下单后仍需按 TST-35 核对订单、明细、版本和购物车。

## 加购响应与徽标核对

TST-08 的分支使用各自独立且满足其他前提的夹具。例如验证合并后大于 99 时，库存准备充分，避免先触发库存不足；验证新第 21 种时，已有 20 行且目标 SKU 尚不在车中。除身份与 CSRF 专项外，均使用启用 CUSTOMER 的有效会话、合法 CSRF 与可辨认的商品 ID，不依赖校验次序推断结果。

| 分支 | 请求或前置 | 预期状态与不变量 |
| --- | --- | --- |
| 数量格式 | 缺失/空 `quantity`，字母，小数（含 `1.0`）、科学记数或超出整数解析范围。 | 400。不得自动取整、默认成功或改写原车。 |
| 数量直接范围 | `quantity=0`、负数、`100`。 | 400。请求本身不是 1–99 的整数。 |
| 商品 ID 格式 | `productId` 缺失、非数字、非正整数或溢出。 | 400。 |
| 未知/下架 | ID 格式合法，但目标不存在或 `status=DRAFT`，数量合法。 | 404。已有同商品的失效行不因此被删除。 |
| 售罄 | 已上架，当前 `stock=0`。 | 409，原车和库存不变。 |
| 库存不足 | 单次或合并后数量超过当前库存。 | 409，不部分加量。 |
| 合并数量上限 | 原数量 99，再加 1；库存足够。 | 409。合并结果超过 99，属于业务冲突，区别于直接输入 100 的 400。 |
| SKU 种类 | 原车 20 种，再加一个新 SKU；失效行同样占品种数。 | 409。已存在 SKU 在 20 种时合法累加仍可成功，前提是数量与库存满足。 |
| 无有效身份 | 游客、已退出或禁用后失效的顾客会话。 | 跳本端登录；登录后返回允许的本端 GET 页，由顾客重新确认写入。 |
| 角色或 CSRF | 已认证但非 CUSTOMER 的身份，或缺失/伪造 CSRF。 | 403，且数据库无本次副作用。 |
| 合法成功 | 分别用数量 1 与 99、库存充分的可售商品验证边界，身份、CSRF 和品种限制均通过。 | 303 跳 U05。同 SKU 仅一行，实际增量令条目版本增加；新行版本为 0。 |

TST-09、TST-11 另外逐页检查徽标。在首页、列表、详情、购物车、结算确认、订单列表和详情等所有显示共用用户端导航的页面，使用同一账号和同一已提交数据，徽标须与 `COALESCE(SUM(cart_item.quantity), 0)` 相等。筛选不含商品状态或库存条件。先记录含失效条目的合计，再改量、移除、成功下单、退出和重登，核对每次显示的更新。游客显示 0，不能误用前一账号的浏览器缓存。加购或改量失败时徽标保持原值；订单提交后仅本次已确认条目清理，新加购条目仍计入。

| TST-17、TST-35 | 同账号两份提交使用同一有效确认令牌，另用不同账号和各自确认同时争抢一件。记录同步起点和应用返回后才查询结果。 | 同确认最多成功一次，后续加购不被旧请求清理。不同账号争抢时仅一个账号有新增订单和明细，库存为 0，失败账号车保留。区分应用层测试与单纯数据库锁探针。 |
| TST-20–TST-24 | 记录待支付单的三项支付字段和商品版本。模拟失败、成功、重放成功，再尝试已付款单的模拟失败或取消。对另一单覆盖下架后返库、重复取消、返库中途故障和支付取消竞争。 | 模拟失败三项支付字段仍为空。首次成功留下原凭证与时间，重放保留原值。已付款后失败或取消返回 409。待支付首次取消只返一次，不回填车，下架状态保留。失败分支无部分返库。 |
| TST-25–TST-27 | 创建 1 字符与 21 字符的一级编码并生成二级，再以 22 字符拒绝分支、重复大小写编码、同父同名、同主题重复类型及非法父类复测。尝试删除带子类或被草稿引用的类目。新建商品用未占用 SKU，检查草稿、上下架及版本冲突。 | 只有合法变更提交。自动发号的分类按回填 ID 可查。21 字符加 `_STATIONERY` 得到 32 字符；22 字符一级编码返回 400 且不写入。重复或被引用删除返回 409，保留关联。商品草稿不公开，上架或下架只影响对应公开目录和详情。 |
| TST-27、TST-28 | 编辑表单尝试篡改 SKU、库存，再用旧版本提交资料。补货校验 0、负数、小数和溢出。另按库存 10、购买 2、补货 3 执行双端并发。 | 编辑入口保留原 SKU、库存，旧版拒绝。非法补货无库存或版本变化。并发成功分支库存为 11、商品版本共增加两次，两个结果与各自请求对应。 |
| TST-29、TST-36 | 对待支付、已取消、已支付、已发货和已完成订单尝试发货。P1 启用时另覆盖本人收货、重复收货及其他人收货。 | 首次发货仅能从待发货进入已发货，已发货或已完成重复发货保留原时间。待支付、已取消返回 409。收货只改变本人已发货订单的状态与首次完成时间，库存和支付字段保持原值。 |

### 新管理功能的失败与并发细分

| 用例 | 补充步骤 | 核对与证据 |
| --- | --- | --- |
| TST-37 | 对上架库存 0 商品、管理员账号、待支付和已发货单逐项做对照，再把一张待支付单模拟支付为 PAID、发货为 SHIPPED。 | 商品仍计上架，ADMIN 始终不影响两个顾客计数；待发货数只在进入/离开 PAID 时增/减 1。同页查询使用一次聚合或同一只读快照；受控无并发状态下与独立 SQL 完全一致。 |
| TST-38 | 用含 `%`、`_` 的独立用户名，另选无订单顾客；按 `userId` 过滤后组合合法和另一顾客的订单号。 | 用户名字面匹配，总数同条件。无订单显示正常空态。指定顾客与另一顾客单号的交集为空，不放宽 `userId`。ADMIN 的列表、详情、状态或订单筛选入口均不可伪装成 CUSTOMER。 |
| TST-39 | 记录 `updated_at`，首次启停后再重复同状态。测试禁用前已登录的两个独立会话，再启用后尝试使用两份原会话。另独立执行禁用→立即启用，两个旧会话在中间均不访问，并覆盖同一微秒内快速切换。 | 重复写保留更新时间；两个会话各自在下一次受保护请求失效。启用不恢复已清除会话；中间未请求的旧会话也因 `authStamp` 与当前 `updated_at` 不一致而拒绝。真实切换的时间须通过 `GREATEST` 至少推进 1 微秒，重复同态保留原戳。受保护写在用户行锁内复查状态、角色和认证戳，不能仅依赖入口已通过的校验。与下单并发时按用户行锁串行化，先前已经持锁并成功提交的业务留存，禁用完成后的新受保护请求不能开始有效写入。 |
| TST-40 | 先取商品 P 的编辑页版本 V，再通过相册实际变更，提交旧商品编辑；反向在取相册版本后补货或下单。再把 Q 的图片 ID 配到 P 的路径。 | 版本竞争一方收到 409 并刷新，不覆盖已提交状态。操作者先锁定并复核身份后，父商品按 `FOR UPDATE` 锁定再核对版本，跨父图片 404。拒绝后 P/Q 相册及商品版本无本次修改，锁定和版本条件不能仅由页面按钮承担。 |

| TST-40 | 为同一商品保留一个相册行，删除后检查产品封面、共享文件及已有订单快照。另让两个商品复用同一路径并删除其一的相册记录。 | 删行不删文件、不改另一商品、不改封面或快照。无相册后详情回封面，封面缺失再回共享占位图。源文件与双端 HTTP 证据明确路径、类型、状态和字节。 |

## 双端演示顺序

1. 管理员查看控制台五项真实计数，按主题进入分类和商品管理，检查新建或编辑商品的相册记录。用独立普通顾客查看详情和关联订单，再执行一次禁用、拒绝原会话、启用及重新登录。测试账号恢复后开始交易演示。
2. 管理员将种子礼盒 `CSU-GRAD-BOX-01` 下架再上架，游客从毕业专区检查商品随状态变化。新增商品另跑 TST-25，预先确认测试 SKU `CSU-GRAD-BOX-QA-01` 未占用。
3. 在隔离测试库用 `alice` 登录，用页面移除操作清空全部种子条目，确认空车。只加入 2 本 `CSU-LMK-NOTE-01`，每本 18.00 元，以及 1 盒 `CSU-GRAD-BOX-01`，每盒 49.00 元。确认只有两条，数量为 2 和 1，合计 85.00 元，再提交。记录主单、明细、库存和购物车。
4. 对演示新订单先模拟支付失败，再成功。管理员按完整订单号查单并发货。两端核对同一订单的快照、金额与发货状态。
5. 另建待支付订单验证取消返库存。独立执行旧确认、故障回滚、支付与取消竞争、同车并发提交、双账号争抢最后一件以及双端购买与补货。
