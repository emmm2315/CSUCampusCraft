# STEP08 backend implementation review

- Candidate scope: five new Java files in the user project's `checkout/` package and the explicit default TTL property in user `application.yml`. No existing auth/cart/foundation Java, admin, SQL, dependencies or POM edits.
- Request order: existing AuthFilter and CsrfFilter remain authoritative; the service checks the session identity and safe CUSTOMER projection, then validates the latest token and expiry, rereads the full current cart using CartService.read, compares item IDs/product IDs/quantities/item versions/unit prices and total, and finally checks shipping fields.
- Session synchronization covers token replacement and validation including ordinary cart reads. Identity is captured before entering the monitor and rechecked exactly inside it to reject a concurrent identity change. This is a Java session monitor, not a database business lock. There are no mapper writes, CustomerWriteGuard calls or SELECT FOR UPDATE statements.
- A confirmation is detached and immutable: a copied immutable list of CheckoutLine records, immutable BigDecimal/Instant values, primitive identifiers/quantities/version, and a 32-byte SecureRandom token encoded as 43-character unpadded Base64url. Creation/expiry use UTC Instant; expiry is inclusive at now >= expiresAt.
- Config: `csucampuscraft.checkout.confirmation-ttl`, default `PT10M` both in YAML and constructor fallback. Zero, negative, malformed or unrepresentable TTL fails construction. Confirmation expiry is fixed at creation; expired data is lazily removed upon validation, reopening replaces it, existing SessionSupport clears it on reauthentication, identity clear or logout/session end.
- Empty/invalid cart and amount overflow are 409; both opening a new invalid confirmation and validation conflicts clear the session's current confirmation. Missing, malformed, duplicate, replaced, cross-session or cross-user tokens are uniformly 409 CHECKOUT_CONFIRMATION_INVALID, disclosing no foreign confirmation. Conservatively, an invalid token also ends any newer current confirmation in that submitting session.
- Amounts are recomputed from current server prices with BigDecimal, exact scale two and positive DECIMAL(12,2) bounds for every unit, subtotal and running total. Browser amount or line fields are never read. Stock is checked for current sufficient availability, not reserved or captured as a lock.
- Shipping fields use InputChecks.requiredText: strip and Unicode code-point lengths 1–50 / 1–30 / 1–255. Duplicate shipping fields are 400, checked after token/cart checks. All field errors are aggregated. Invalid input values remain request-scoped for escaped SSR correction; none enter the session confirmation. No code logs receiver fields, tokens, hashes or request parameters. Snapshot, validation and shipping toString outputs redact potentially sensitive contents.
- Fully valid POST returns 409 ORDER_SUBMISSION_PENDING, explicitly saying STEP09 will add order submission and no order/cart/stock was written. It retains the valid confirmation because no submission succeeded. STEP09 must replace this stub with the documented RC user/product-lock write transaction; this read-only validation is not a substitute for write-time revalidation.
- A broad IllegalStateException handler checks whether the HttpSession has actually expired. An unrelated technical IllegalStateException remains on the generic 500 path instead of being mislabeled as an authentication failure.
- Static formatting check: all six candidate files UTF-8, LF, single final newline, no tabs. This note is a source review, not runtime acceptance. Real builds, HTTP/database, expiry and native probe results are owned by the root acceptance run.
