# CSUCampusCraft 验收与联调清单

INIT 项验证工程初始化。AC-01 至 AC-32 验证首个完整业务版本，CAMP-01 至 CAMP-03 验证毕业专区、成品礼盒和双账号争抢最后一件，AC-33 和 AC-34 随实际选做范围执行。组员版指导书使用 CSU-V01 至 CSU-V16，课程 PRD 的 V01 至 V18 单列。业务场景按[开发任务与版本路线](开发任务与版本路线.md)推进并单独记录。

配套文档见[项目需求与双端设计](项目需求与双端设计.md)、[系统架构与共享数据契约](系统架构与共享数据契约.md)和[组内开发协作指南](组内开发协作指南.md)。

另验证了 PostgreSQL 行锁机制。在两个独立连接中，第二个事务等第一个事务把库存从 1 扣到 0 并提交，随后 `SELECT … FOR UPDATE` 读到 0。完整的 CAMP-03 还需在下单服务实现后验证成功订单和失败方购物车。下文的 AC、CAMP 和选做场景按业务版本执行。

## 业务联调准备

- 从提交候选版本构建两个独立工程，连接同一套可恢复的测试数据库。记录 Git SHA、JDK、Maven、PostgreSQL、浏览器版本、启动命令和实际访问地址。用户端使用 `8080` 和 `CSUCAMPUSCRAFT_USER_SESSION`，管理端使用 `8081` 和 `CSUCAMPUSCRAFT_ADMIN_SESSION`。
- 验收数据按 PRD 第 28 页的示例规模准备 4 个账号、15 个分类、60 个商品、100 条相册图片记录、10 条购物车条目、10 张订单和 20 条订单明细。初始 5 个主题各有两个二级类目，每个二级类目 6 个商品。商品企划中的约 20 个 SKU 用于确定代表性设计，其他条目用于补齐验收数据。两个启用的普通账号各有五种状态的历史样例，已完成状态可由种子数据提供。
- 准备可跨主题筛选的数据和独立边界夹具。首页两栏分别准备超出展示上限的数据，列表准备能翻页的结果集，购物车限额测试确保至少有 21 个可加购 SKU。覆盖库存为 1、零库存上架、下架、无相册、缺图、确认后改价和已有订单引用的商品。订单联动证据用真实页面操作产生的新订单。
- 在桌面 Chrome 或 Edge 的 1366×768 和 1920×1080 视口走主流程。检查筛选、数量输入、结算提交及发货等关键控件可见、可操作。
- 用测试账号、模拟地址和测试商品取证。并发、取消、回滚等会改动数据的场景各用可重置夹具，按初始化说明重建测试状态。数据恢复操作与应用常规启动分开执行。

## 双端演示顺序

1. 管理员将种子礼盒 `CSU-GRAD-BOX-01` 下架再上架。游客从毕业专区进入分类列表，分别检查下架和上架时的可见性。新增商品另按 AC-25 验证，预先确认 `CSU-GRAD-BOX-QA-01` 未占用。
2. 普通用户登录，加入 2 本潇湘校区图书馆方格本和 1 盒中南毕业纪念礼盒（`CSU-GRAD-BOX-01`）。测试单价分别为每本 18.00 元和每盒 49.00 元，整车总额应为 85.00 元。下单后查询订单主记录、两条明细、各自库存和购物车。
3. 先模拟支付失败，再模拟成功。管理员按完整订单号查单并发货。用户刷新订单，核对相同的商品快照、金额和状态。
4. 另建待支付订单验证取消返库存。用独立测试数据执行故障回滚、支付取消竞争、同车并发下单、两账号争抢最后一件，以及两个应用同时购买和补货。

### 购物车与下单

| 编号 | 操作 | 通过条件 |
|---|---|---|
| AC-08 | 重复加入同 SKU，再提交 0、负数、小数、100、合并后超量和第 21 种 SKU | 合法数量合并为一行。非法数量、合并后超出 99 或库存、超过 20 种均拒绝写入。 |
| AC-09 | 加购后退出、重启、重登，再换浏览器或普通账号查询 | 同账号可恢复数据库购物车。其他账号只看到各自的购物车。 |
| AC-10 | 跨账号改数量或删除条目，再提交本账号条目的旧版本 | 越权与旧版本请求均被拒绝。数据库保留当前合法数据。 |
| AC-11 | 将车中商品下架或使其售罄，再尝试结算和移除 | 购物车保留该条目，标出失效原因，阻止整车结算并允许移除。 |
| AC-12 | 分别提交空地址、超长地址，以及收货信息合法但金额字段被篡改的请求 | 地址非法时无订单、库存及购物车写入。金额从服务端商品价和数量计算，客户端字段无法影响成交价。 |
| AC-13 | 打开确认页后后台改价，或同账号另一会话修改数量、新增条目，再提交旧确认 | 旧确认提示重新确认。订单、库存和购物车无本次下单副作用，新加入条目仍可查询。 |
| AC-14 | 正常提交两种商品，数量分别为 2 和 1 | 一条待支付主记录、两条明细，快照和金额正确。两项库存分别扣 2 和 1，商品版本递增，已确认条目清理。 |
| AC-15 | 确认后使其中一种商品库存不足或下架，再提交整车 | 整笔失败。无新增订单或明细，两项商品均无下单库存变化，车中原条目仍可查询。 |
| AC-16 | 在写订单、扣首项库存和删除已结算条目后的故障点分别注入测试异常 | 每个故障点下，订单主表、明细、全部库存、版本和购物车均回到该次下单前的状态。 |
| AC-17 | 同账号两会话并发加同商品、提交旧版本修改、提交同一车。分别验证数量和种类边界 | 相同 SKU 只有一行，数量和种类约束生效。旧版本无法覆盖有效写入。同车只成交一次。后续加购归新车，成功订单的清理只覆盖已确认条目。 |

### 订单状态与后台联动

| 编号 | 操作 | 通过条件 |
|---|---|---|
| AC-18 | 甲尝试打开乙的订单或执行支付、取消，并篡改表单 `user_id` | 后端以当前会话身份判断。请求被拒绝，乙的订单详情、状态和库存均未因该请求暴露或变动。 |
| AC-19 | 下单后修改商品名称、价格、封面或上下架状态，再查历史订单并支付仍有效的待支付订单 | 两端读取创建时快照，金额、明细和收货信息一致。有效待支付订单按原金额模拟支付。 |
| AC-20 | 模拟支付失败后成功，再重复提交成功 | 失败时仍待支付且无成功凭证。首次成功转 `PAID`，写入 `MOCK`、凭证和时间。重复请求保留首次凭证及时间，支付过程库存无额外扣减。 |
| AC-21 | 取消含两条明细的待支付订单，再重复取消 | 首次转 `CANCELLED`，按明细返库存并维护版本。第二次无额外返库。用户再次购买需重新加购。 |
| AC-22 | 下单后下架商品，再取消并尝试支付和发货 | 下架商品库存按明细恢复，仍为 `DRAFT`。已取消订单的支付、发货请求被拒绝。 |
| AC-23 | 取消中恢复首项库存后注入异常 | 订单仍待支付，取消时间为空，全部商品库存及版本回到取消前。 |
| AC-24 | 同一待支付订单在独立事务内同时支付和取消 | 只发生一种状态迁移。若支付胜出则为 `PAID`，有首次支付凭证且库存保持下单扣减后的值。若取消胜出则为 `CANCELLED`，无支付成功凭证且库存只返一次。 |
| AC-25 | 后台新增合法分类和商品，上架前后检查前台。尝试三级分类、非法父级或将商品直接挂到一级 | 合法新增数据在两端一致。未上架商品不可购买。三级及非法归属写入被拒绝。 |
| AC-26 | 删除有子分类的一级类目、被下架商品引用的二级类目，再删除无子分类且无引用的类目 | 有子分类或引用的删除请求被拒绝，商品和订单历史完整。空类目可以删除。 |
| AC-27 | 打开后台商品编辑页，用户下单或取消改变库存后，再提交旧表单 | 提示版本冲突。数据库仍为用户操作后的库存和版本。 |
| AC-28 | 启动两个真实应用，用户端购买 2 件与管理端补货 3 件同时作用于同一 SKU，初始库存 10 | 两项业务均成功，库存为 11。订单与明细、补货、库存和版本变化可对应到两端请求。另用失败夹具验证失败分支无部分写入。 |
| AC-29 | 尝试发货待支付订单，支付后再发货，随后重复发货 | 只有 `PAID → SHIPPED` 成功。两端可查发货状态，重复提交保留首次发货时间。 |
| AC-30 | 按五状态及完整订单号搜索，尝试部分单号、切换账号、翻页及提交非法参数 | 仅返回本人的精确匹配结果，分页保留查询条件。无结果与非法参数分别走对应状态，旧查询结果不会串到其他账号。 |
